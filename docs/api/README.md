# API 版本总览

本目录是 BSK API 的**版本化事实来源**。每个已发布的版本都有独立目录，**互不覆盖** ——
老版本的接入方永远能找回当时那份契约，不会因为服务升级而失去适配依据。

| 版本 | 状态 | 服务端生成文案 | 响应信封 | 契约文档 |
|---|---|---|---|---|
| **`v1-261001`** | **当前版**（最新） | 英文 | 有 `api_version` / `locale` / `schema` | [v1-261001/README.md](./v1-261001/README.md) |
| `v1-260925` | **冻结**（历史版） | 中文 | 无 | [v1-260925/README.md](./v1-260925/README.md) · [原文快照](./v1-260925/REFERENCE.md) |

## 路径怎么解析

| 写法 | 实际走的版本 | 什么时候用 |
|---|---|---|
| `/api/<端点>` | **最新版**（当前 `v1-261001`） | 随便写写、临时调 |
| `/api/<端点>/v1` | **最新版**（当前 `v1-261001`） | 想写明"我用 v1"，但接受它以后会跟着最新版变 |
| `/api/<端点>/v1-261001` | 钉死在 `v1-261001` | **接进生产代码**，不想某天被上游改字段搞挂 |
| `/api/<端点>/v1-260925` | 钉死在 `v1-260925`（旧中文契约） | 已有集成吃的就是老格式，暂时不动 |

- 版本号是**路径最后一段**：`/api/player/card/v1-261001` → 端点 `player/card` + 版本 `v1-261001`。
- **`v1` 是"最新版"的别名，不是"第一版"。** 它当前指向 `v1-261001`；等发布新版本它会跟着走。
  要长期稳定就用**带日期的版本号**。
- 不认识的版本（含拼错的日期、以及**还没发布的未来日期**）→
  `404` + `{"ok": false, "error": "unknown_version"}`，响应有 `latest`；支持版本目前列在 `message` 中，并无 `endpoints` 数组。

> ⚠️ **只有 `v1-260925` 这一串字符被特殊对待。** 服务端判定"是否走旧契约"是一次
> **字符串精确比较**，只有 `v1-260925` 返回旧格式。公布版本是表中三项，
> 其它日期（例如 `v1-250101`）返回 `404 unknown_version`。无日期的旧主版本（如 `v0`）存在未公布兼容分支，不推荐使用。

## 响应头

版本解析成功并经 `_json()` 输出的响应带版本头；未知版本、并发拒绝和透明反代原始响应没有版本头：

| 响应头 | 含义 |
|---|---|
| `X-API-Version` | **本次实际走的版本**。注意它回显的是**你请求的那一段**（写 `/v1` 就回 `v1`），不是解析后的完整版本号 |
| `X-API-Latest` | 当前最新版本的完整号（现在是 `v1-261001`） |
| `X-Quota-Cost` | 按响应体大小计算的理论价格，不等于实际结算金额；`/api/quota` 在任何状态码下为 `0` |
| `Retry-After` | 撞限速时给出建议等待秒数（429） |

响应体里还有 `api_version`（**写死的完整版本号**，与请求头 `X-API-Version` 的语义不同）、
`locale`、`schema`。见[当前版契约](./v1-261001/README.md#3-响应信封)。

## 端点清单（机器可读）

```
GET /api
```

不带端点路径时回一份**发现文档**，包含：

- `latest` / `latest_alias` / `versions` —— 当前版本、别名、全部可用版本
- `parameters` —— **全部 24 个永久参数 ID 的注册表**（含 `key` / `name` / `location` / `type` / `required` / `description`）
- `parameter_id_policy` —— ID 的规则（全局顺序、不可变、不复用）
- `endpoints[]` —— 每个端点的 `latest` / `versioned` / `alias` / `desc` / `auth` / `parameter_ids[]`
- `hypixel_proxy` / `bugland_proxy` —— 两个透明反代的 base 与鉴权方式

看到新端点、新参数以它为准；本文档与它不一致属文档缺陷，请提 issue。

## 参数 ID

每个已注册请求参数有一个**永久的数字 ID**，是公开契约的一部分：
[parameter-registry.md](./parameter-registry.md)。规则是**只追加、不复用、不改含义** ——
删除参数后它的 ID 也不会被重新分配给别的参数。

参数 ID 描述的是**你用的那个请求参数**，不是响应里的字段。响应里的 `id` / `code` /
`state` / `source` 等是**业务数据**，与参数 ID 无关，不要混用。

## 与当前版本的迁移

从 `v1-260925` 升到 `v1-261001`，主要差异为：

1. **服务端生成的文案从中文变英文**（标签、错误说明、卡片块标题等）。
   玩家名 / 公会名 / 披风名 / 上游原样字段**不受影响**。
2. **响应信封多了 `api_version` / `locale` / `schema`** 三个顶层字段。
3. **`/api/bancheck` 多了 `state` 和 `data_quality`** 两个机器字段。
4. **`/api/player/card` 加入 `ban_status` 与封禁展示块**；旧版不包含它。

版本分支共用当前额度规则，但历史服务器并非独立冻结；快照里的旧计费说明不一定仍然有效。详细的逐项差异见
[v1-260925 的版本差异一节](./v1-260925/README.md#与-v1-261001-的差异)。

## 维护说明（重要）

> 本目录**必须**与服务实现同步。改动以下任何一项时，**同一次变更**里就要更新对应版本文档：
>
> - 新增/删除/重命名任何 `/api/*` 路由或别名
> - 请求参数（含新增参数 → **必须追加新的永久 ID** 并同步 `parameter-registry.md`）
> - 响应字段、错误 `error` 取值、状态码
> - 额度、限速、缓存、闸门
> - 服务端生成文案的语言或翻译边界
>
> **绝不修改已发布版本的既有语义。** 行为要有变化就发新版本号，让老版本继续按老契约跑；
> 新版本另开目录。改旧目录等于单方面撕毁对老接入方的承诺。
>
> 服务实现仓库里 `tests/test_api_documentation.py` 会校验版本文档与注册表存在且一致 ——
> 该测试保护服务仓库中的文档与参数目录存在性，不代表本仓库全部示例都已端到端验证。本仓库另运行 `tools/check_docs.py` 与 `tools/check_contract.py`。
